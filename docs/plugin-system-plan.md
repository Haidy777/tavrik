# Tavrik Plugin System — Planning Document

## Context

Tavrik currently ships with a minimal set of built-in personas (Tavrik EN/DE) stored in the database. As the project grows, there's a desire to support community-contributed personas and eventually LLM-callable tools that can be loaded from external repositories.

**Goal**: Design a plugin system that lets users browse, import, and customize content from curated external Git repositories — starting with personas, extensible to tools later.

---

## Terminology

| Term | Meaning |
|------|---------|
| **Registry** | A Git repository (GitHub) containing curated plugin content |
| **Plugin** | A self-contained unit of content (persona, tool) that can be imported |
| **Manifest** | A `manifest.json` file describing a plugin's metadata |
| **Index** | A generated `index.json` at the registry root for fast browsing |
| **Local copy** | A plugin imported into the user's Tavrik database, editable freely |

---

## Design Principles

1. **Curated registries** — each registry is a reviewed, maintained Git repo (e.g. `tavrik/personas`, `tavrik/personas-nsfw`, `tavrik/tools-advanced`)
2. **Import, not link** — plugins are copied into the local database on install; no runtime dependency on the remote repo
3. **Edit after import** — users own their local copy and can modify it freely
4. **No code execution for personas** — persona plugins are pure data (JSON); tool plugins will need a sandboxing strategy (phase 2)
5. **Multiple registries** — users can add multiple registry URLs (public community repo, private repos, forks)

## Phase 1: Persona Plugins

### Registry Repository Structure

A persona registry repo (e.g. `tavrik/personas`) follows this layout:

```
tavrik-personas/
  index.json                      # auto-generated, lists all personas
  personas/
    research-assistant/
      manifest.json               # metadata
      persona.json                # content (system prompt, modifiers, etc.)
    code-reviewer/
      manifest.json
      persona.json
    creative-writer/
      manifest.json
      persona.json
  .github/
    workflows/
      build-index.yml             # CI: regenerate index.json on merge
  scripts/
    build-index.ts                # reads all manifest.json, outputs index.json
  CONTRIBUTING.md                 # guidelines for persona contributions
  schema/
    manifest.schema.json          # JSON Schema for manifest validation
    persona.schema.json           # JSON Schema for persona validation
```

### Manifest Format

```json
{
  "id": "research-assistant",
  "name": "Research Assistant",
  "description": "Focused on academic research with citation support",
  "author": "contributor-name",
  "version": "1.0.0",
  "tags": ["research", "academic", "citations"],
  "languages": ["en"],
  "tavrikVersion": ">=1.0.0"
}
```

### Persona Content Format

```json
{
  "personas": [
    {
      "name": "Research Assistant",
      "language": "en",
      "systemPrompt": "You are a research assistant specialized in..."
    },
    {
      "name": "Forschungsassistent",
      "language": "de",
      "systemPrompt": "Du bist ein Forschungsassistent, spezialisiert auf..."
    }
  ],
  "modifiers": [
    {
      "name": "Formal Tone",

    },
    {
      "name": "ELI5",
      "systemPromptModifier": "Explain concepts as if to a five-year-old..."

}
```

### Tavrik-Side: Registry Management

#### Database Changes

New table in the `system` schema:

```
system.registries
  id           bigint (PK, generated)
  name         text (e.g. "Community Personas")
  url          text (e.g. "https://github.com/tavrik/personas")
  type         enum('personas', 'tools')
  enabled      boolean (default true)
  lastSyncedAt timestamp (nullable)
  createdAt    timestamp
  updatedAt    timestamp
```

Track import origin on existing persona tables:

```
personas.personas (add columns)
  registryId     bigint (nullable, FK -> system.registries)
  registryItemId text (nullable, e.g. "research-assistant")
  importedVersion text (nullable, e.g. "1.0.0")
```

This allows the UI to show "imported from Community Personas v1.0.0" and check for updates, while still keeping the persona fully editable locally.

#### Fetch Mechanism

Use **raw HTTP fetch** against GitHub's raw content URLs. No git binary required, no heavy dependencies.

```
# Fetch index for browsing
GET https://raw.githubusercontent.com/tavrik/personas/main/index.json

# Fetch specific persona for import
GET https://raw.githubusercontent.com/tavrik/personas/main/personas/research-assistant/manifest.json
GET https://raw.githubusercontent.com/tavrik/personas/main/personas/research-assistant/persona.json
```

For private registries, support a configurable auth token per registry (stored in `system.registries` or a separate secrets mechanism).

#### API Endpoints

```
# Registry management
GET    /api/v1/registries                    — list configured registries
POST   /api/v1/registries                    — add a registry
PATCH  /api/v1/registries/:id                — update registry (name, url, enabled)
DELETE /api/v1/registries/:id                — remove a registry

# Browse remote content
GET    /api/v1/registries/:id/browse         — fetch + return the registry index
GET    /api/v1/registries/:id/browse/:itemId — fetch + return a specific plugin's details

# Import
POST   /api/v1/registries/:id/import/:itemId — fetch persona, insert into local DB
```

#### Import Flow

```
User opens "Persona Store" in UI
  → UI calls GET /api/v1/registries
  → For each enabled registry, UI calls GET /api/v1/registries/:id/browse
  → User sees combined list of available personas with metadata
  → User clicks "Import" on a persona
  → UI calls POST /api/v1/registries/:id/import/research-assistant
  → API fetches persona.json from GitHub raw URL
  → API inserts persona(s) + modifiers into local DB
  → API sets registryId, registryItemId, importedVersion on new records
  → Persona appears in user's persona list, fully editable
```

#### Update Detection

When browsing, the API can compare `importedVersion` against the registry's current version to show an "Update Available" badge. Updating re-imports (overwrites or creates new version — TBD based on UX preference).

## Phase 2: Tool Plugins (Future)

Tool plugins are fundamentally different from personas because they involve **executable code**. This section outlines the direction without committing to implementation details.

### What is a Tool Plugin?

An LLM-callable function (e.g. weather lookup, calculator, web search) that:
- Has a JSON Schema describing its parameters (for the LLM)
- Has executable logic (TypeScript/JavaScript) that runs server-side
- Returns structured results back to the LLM

### Registry Structure (Tools)

```
tavrik-tools/
  index.json
  tools/
    weather/
      manifest.json         # metadata + parameter schema
      tool.json             # tool definition (name, description, parameters JSON Schema)
      handler.ts            # the actual implementation
    web-search/
      manifest.json
      tool.json
      handler.ts
```

### Open Questions for Tools

These need research and decisions before implementation:

1. **Execution model** — How do tool handlers run?
   - **Option A**: Compiled/bundled at import time, loaded as dynamic ES modules (`import()`)
   - **Option B**: Run in a sandboxed VM (e.g. `node:vm`, `isolated-vm`) for security
   - **Option C**: Run as separate processes (worker threads or child processes)
   - **Option D**: WebAssembly-based sandboxing (e.g. Extism)

2. **Trust model** — Persona plugins are just data, but tool plugins run code
   - Curated repos with CI validation mitigate some risk
   - Should tools declare required permissions? (network access, file system, etc.)
   - Should there be a "verified" badge system?

3. **Dependencies** — Tool handlers might need npm packages
   - Bundle all deps into the handler? (larger files, simpler runtime)
   - Allow a package.json per tool? (more complex import flow)
   - Restrict to Node.js built-ins only?

4. **Shipping base tools** — Tavrik ships with a default set of tools
   - These live in `src/core/` (or a new `src/tools/` package)
   - External tool plugins follow the same interface
   - Registry tools are additive, they don't replace built-in tools

5. **Private tool repos** — For personal tools that shouldn't be public
   - Same registry mechanism, just with auth tokens
   - Good for "my custom tools" use case

### Tool Plugin Interface (Strawman)

```typescript
// What a tool handler might look like
export interface ToolDefinition {
  name: string
  description: string
  parameters: JSONSchema  // passed to LLM for function calling
}

export interface ToolHandler {
  definition: ToolDefinition
  execute(params: Record<string, unknown>): Promise<ToolResult>
}

export interface ToolResult {
  success: boolean
  data: unknown
  error?: string
}
```

## Implementation Order

### Step 1: Persona CRUD API
Prerequisite — the persona routes are currently a stub. Need full CRUD for personas, modifiers, and user profiles before building import on top.

### Step 2: Registry Infrastructure
- Database migration for `system.registries` table
- Add origin-tracking columns to `personas.personas`
- Registry CRUD API endpoints
- Registry fetcher service in `@tavrik/core` (HTTP fetch + JSON parsing)

### Step 3: Browse & Import API
- Browse endpoint (fetch + cache remote index)
- Import endpoint (fetch persona content, validate, insert into DB)
- Update detection (compare imported version vs remote version)

### Step 4: Persona Registry Repo
- Set up `tavrik/personas` repo on GitHub
- Define JSON schemas for manifest and persona content
- Build the `build-index.ts` CI script
- Seed with a handful of example personas
- Write CONTRIBUTING.md

### Step 5: UI Integration
- "Plugin Store" or "Persona Store" view in the UI
- Browse available personas across registries
- Import with one click
- Show update badges for newer versions

### Step 6: Tool Plugins (Future)
- Research and decide on execution model
- Define tool plugin interface and registry format
- Implement tool loading and sandboxing
- Extend registry system to support tool type

## Open Questions

1. **Caching** — Should the API cache the registry index locally (with TTL), or fetch fresh every time the user browses? A TTL-based cache (e.g. 5 minutes) seems sensible.

2. **Conflict handling** — What happens if a user imports a persona with the same name as an existing one? Options: rename with suffix, overwrite with confirmation, block and show error.

3. **Versioning UX** — When an update is available, should it overwrite the local copy or create a new persona? Overwriting loses local edits; creating a new one causes duplication.

4. **Auth for private registries** — Where to store GitHub tokens? In `system.settings`? In `system.registries` (encrypted column)? In environment variables?

5. **Persona dependencies** — Could a persona depend on specific tool plugins? (e.g. "Research Assistant" works best with a "web-search" tool) — probably not for phase 1, but worth thinking about.

6. **SDK coverage** — Should `@tavrik/sdk` get registry methods, or is this API-only for now?
